The problem

Hundreds of small groups, reported on paper and WhatsApp.

Each week a group leader takes attendance and logs activities and offerings. That data has to reach the pastor, the conference and the union, which meant spreadsheets, photos and phone calls.

Presencia Líder replaces that chain with one system where each person sees only their part of the church.

  1. Union union admin
  2. Conference / Mission campo admin
  3. District pastor
  4. Church elder
  5. Small group leader
  6. Member phone app

The data model mirrors the real church hierarchy. A report starts on the leader's phone and rolls up automatically.

Access control · the technical heart

Each person sees only their part of the church

The policy on meeting only lets a user read groups returned by one helper function. The helper walks church, district, conference and union, and matches each active role assignment of the signed-in user: an elder sees their church, a pastor their district, a conference admin their conference. Wrapped in (select …), it runs once per query rather than once per row, so the check stays fast.

Row-level security everywhere

Every table has policies; nothing is readable just because a screen doesn't show it.

Invite-only accounts

No public sign-up. Credentials are hashed, and people set their own password from an email invite.

Demo and production apart

A separate demo project, so the product can be shown without touching real data.

Audits before real data

Security audits ran before real church data went in, and their findings were fixed first.

Privacy law

A public privacy policy and self-service account deletion, following Costa Rica's Law 8968.

Safe by default

Rate limiting per IP, soft deletes only, and scope checks a pastor can't bypass outside their district.

A bug worth telling

Approve and reject actions called the database with an admin client that carries no user identity, so the policy check saw no user at all. I traced it, moved those calls to the signed-in user's client, and made the guard fail closed.

The web app

Same components, different scope

Row-level security decides which rows come back, so there's no separate code path per role.

Reports

From one group to the whole union

Attendance, studies, visits and offerings by week, month, quarter or year, compared across conferences, districts, churches or groups. Export to PDF, Excel and CSV.

Two details came from real use: the current month is drawn dashed so a half-finished period doesn't read as a drop, and numbers use Costa Rican format (decimal comma, colones).

Performance

About 6× faster, same results row for row

930 → 155 msunion yearly report, database time
190 → 70 msquarterly report, database time
  • Measured with EXPLAIN ANALYZE under each role's permissions, on realistic data.
  • Moved the math into Postgres: one aggregating function instead of fetching thousands of rows into JavaScript.
  • About 12 sequential queries now run in parallel.
  • Tabs and charts load when opened, with indexes on the large tables.

Analytics layer

Dashboards that never touch production

A separate analytics schema with materialized views and at-risk snapshots (members drifting away, inactive groups, lapsing visitors), feeding Metabase dashboards that read from a cron-synced replica, never from production.
