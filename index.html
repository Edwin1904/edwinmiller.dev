Presencia Líder

3 developers + faculty advisor · web & backend lead

A platform where Adventist churches in Costa Rica track weekly small-group meetings, attendance and activities, from the local group up to the national union. It replaces paper reports that leaders often never turned in. Built by three student developers (Android, iOS, and me on web and backend) with a faculty advisor.

188database migrations
52pages in the web app
7roles, each with its own scope
296real congregations loaded
Next.js 16TypeScriptTailwindPostgreSQLSupabaseRow-level securityMetabaseVercel
  • Access control in the database. Row-level security policies and a helper function walk church → district → conference → union, so each role only sees its own scope. The rules live in Postgres, not in app code.
  • Reports across the whole hierarchy. Attendance, studies, visits and offerings by week, month, quarter or year, compared across conferences, districts, churches or groups, with PDF, Excel and CSV export.
  • Faster queries, same results. Moved report summing into the database and cut the yearly report from 930 ms to 155 ms (6×) and the quarterly one from 190 ms to 70 ms. Old and new outputs were compared with EXCEPT ALL: zero rows differ.
  • Shared backend for mobile. Defined the data contracts the Android and iOS apps build on, so all three clients work from one schema.
  • Analytics layer. A separate analytics schema with materialized views and at-risk snapshots (members drifting away, inactive groups, lapsing visitors), feeding Metabase dashboards that read from a replica synced by cron, never from production.
  • Approved for rollout. Signed off by UNADECA and the union for all three Costa Rica missions plus UNADECA's theology students.

Fantasy Predictor

Started as a Data Structures course project

An end-to-end data project built on a fantasy football API: a Postgres backend under real load, an ETL that cleans messy department data into a reporting layer, dashboards on top, and match predictions.

ExpressTypeScriptPostgreSQLETLData martMetabaseDockerTerraformk6Poisson model
  • ETL from messy data. Pulled deliberately inconsistent sources (an Excel ledger, a SQLite database and Notion JSON exports) through a custom ETL into a mart layer, logging every run and every rejected row.
  • Dashboards on top. Four Metabase dashboards read from the mart, so every number comes from one cleaned source.
  • Infrastructure as code. Terraform defines the stack, from Docker locally to an AWS-style setup with a database, compute, S3 landing zone and scheduled jobs.
  • Load tested, bottleneck found. A 1M-row schema under k6 load showed Postgres CPU climbing past the API's. I traced it to connection-pool oversubscription (about 160 connections on 8 cores) and resized the pool to 48.
  • Match predictions. A Poisson model predicts match scores from each club's attack and defense strength, with a Dixon-Coles upgrade next.
